2. Trois corrections au rapport Pointage

2.1 Un seul plafond de pause, pas deux

Le rapport propose un « seuil pause suspecte = 2× la prévue (≈ 3h) ». Or pause_duree_max_minutes existe déjà et vaut 120 minutes par défaut (…pauses_intelligentes.sql:581).

Ajouter un second plafond créerait deux vérités pour une même pause — exactement le défaut que le fichier src/services/seuilsPointage.js a été écrit pour empêcher. Sa règle, en tête de fichier, vaut pour les deux ateliers : « Aucun seuil de pointage ne doit être réécrit en dur dans un composant, une page ou une fonction SQL. Les valeurs par défaut ci-dessous sont le CONTRATOIRE, pas un réglage. »

Décision technique : si le fondateur veut un autre plafond (90 min, 180 min…), c'est cette clé qui change, une seule fois. Aucun second seuil n'est créé.

2.2 « Pause déduite oui/non » n'est pas un réglage d'affichage

La règle existante est déjà nuancée, codée et testée :

  • pause pointée → déduite ;
  • pause présumée non validée → non déduite (« Présomption non validée : on marque, on n'encaisse pas », pausesService.js:153-156) ;
  • pause écartée → jamais déduite (:150-151).

Un interrupteur binaire aplatirait cette nuance. Et la pause payée est une décision de politique de paie, pas d'affichage : si elle était réglée sur la tablette, la tablette dirait 3h16 et le bulletin paierait 4h54.

Décision du fondateur (point 2, actée) : on n'ajoute pas ce réglage maintenant. L'affichage Admin montre Présence / Pause / Travaillé, aligné sur la règle existante. « Pauses payées » reste un chantier de paie séparé, à ouvrir seulement si un client le demande.

2.3 Le 3e bouton employé doit laisser une trace de provenance

La colonne source est fermée par contrainte à ('pointee','presumee','admin') (…pauses_intelligentes.sql:90). Une correction faite par l'employé ne peut donc pas être distinguée aujourd'hui d'une correction du manager.

Décision du fondateur (point 3, actée) : le bouton est accepté. Côté Admin, cela implique :

  • ajouter 'employe' à la contrainte source (migration petite et réversible) ;
  • tracer chaque correction via encheck_journal_tracer (motif + action), pour que « qui a attesté quoi » reste lisible dans six mois ;
  • n'accepter ce bouton que dans la zone suspecte, jamais dans le cas normal.

3. Ce que l'Admin doit construire

3.1 L'écran « Temps de travail »

Constat : aucun écran n'édite aujourd'hui le registre des seuils. Les valeurs sont semées en base, lues par encheck_seuil() côté SQL et par chargerSeuilsPointage() côté application (src/services/seuilsPointage.js) — mais aucune page ne permet de les régler.

Décision du fondateur (point 1, actée) : l'écran vit dans Configuration pointeuse → onglet « Temps de travail ». Un seul lieu, pas un cinquième endroit dans la navigation.

Il regroupe tous les seuils par thème : Sessions & oublis, Pauses, Estimation, Anti-rebond, Alertes. Chaque champ affiche son rôle et sa valeur par défaut — le registre porte déjà un commentaire par clé (:107-126) : c'est la meilleure documentation possible, autant la réutiliser telle quelle.

3.3 Le contrat d'écriture (décision du fondateur, point 4, actée)

« Clôturer la pause et enregistrer la sortie » touche deux tables : attendances et encheck_pauses. La tablette ne peut pas garantir l'atomicité seule, surtout hors ligne.

Contrat :

  1. une opération serveur unique (un RPC) reçoit la sortie et clôt la pause dans la même transaction ;
  2. elle porte une clé d'idempotence fournie par la tablette (le jeton d'intention) : rejouer le même jeton ne crée pas de seconde sortie ;
  3. la règle « aucune écriture directe dans attendances » interdit de contourner le canal, pas d'écrire par le canal prévu. Le RPC est le canal.

Sans ce contrat écrit, l'atelier Pointage ne doit pas développer le jeton d'intention : il produirait deux écritures non atomiques et laisserait des pauses orphelines — le défaut même que l'on corrige.

3.4 La file « à vérifier » côté Admin

Les anomalies de pause existent déjà et la page Pauses permet de les trancher. Reste à couvrir dans un seul endroit lisible par le manager :

  • pauses sans_reprise et trop_longue (déjà calculées) ;
  • journées non terminées — le seuil existe déjà : oubli_sortie_heures = 12 (20261016000001:107).

5. Ce que l'Admin confirme sans réserve

Tout le reste du rapport Pointage est compatible avec le schéma actuel et validé côté Admin :

  • la machine à états (hors service / en service / en pause / journée terminée) ;
  • la règle de borne — la sortie clôt la pause au même instant, sans jamais inventer d'heure passée ;
  • les deux dialogues de confirmation et leurs libellés (à valider par le fondateur) ;
  • le jeton d'intention anti-double-tap ;
  • le retour optimiste avec budget de 0,5 s et mesure anonyme des latences ;

  • la réconciliation « à vérifier », jamais de correction automatique du passé ;
  • l'affichage Présence / Pause / Travaillé.

9. Ce que cette note ne couvre pas

  • Le motif exact des décisions historiques : à relire dans le journal d'audit avant toute reprise (encheck_journal_tracer), jamais modifié.
